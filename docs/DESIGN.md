# Pixel Frontier · Design & Implementation Notes

## 1. Scope

V0.1 — законченный вертикальный срез, а не offline-макет. Одиночный и сетевой режимы используют одну авторитетную симуляцию, один протокол и одни формулы. Пользовательский клиент не имеет API для непосредственного изменения ресурсов или владельца.

Вне scope: аккаунты/Elo, союзы и дипломатия, fog of war, сценарный редактор, реплеи, PWA-установка, кастомные флаги, достижения и магазин.

## 2. Карта

`tools/buildMap.js` создаёт `shared/map/map.json` и `map-large.json`:

1. Континентальные полигоны и островные эллипсы растеризуются в 192×96.
2. Отдельные компоненты суши получают по стартовому seed, поэтому остров не остаётся без региона.
3. Остальные seed-точки выбираются farthest-point sampling с небольшим детерминированным jitter.
4. Multi-source flood fill по 4-связности назначает каждой клетке регион. Каждый регион связен по построению.
5. Из границ клеток выводятся сухопутные соседи, центроид, площадь и береговая линия.
6. Пары прибрежных регионов на расстоянии ≤6 получают `seaNeighbors`; атака по такой связи требует порта.

Результат: **7021 клетка суши**, 300 или 350 регионов. Карта хранит статическую геометрию; `ownerId`, войска и постройки существуют только в `GameRoom`.

Пересоздание карт:

```bash
npm run build:map
npm test
```

## 3. Детерминированный цикл

`RoomManager` компенсирует elapsed time с ограниченным catch-up budget. Каждая комната получает фиксированный шаг 50 мс. `speed` умножает только dt внутри симуляции, а не серверный scheduler.

Порядок активного тика:

1. Очередь команд и idempotency.
2. Disconnect/transfer logic.
3. Пересчёт агрегатов игроков.
4. Рост войск и экономики.
5. Автоматические постройки.
6. Волны атак и разрешение захватов.
7. Дроны, ракеты и ПВО.
8. Решения ИИ.
9. Повторный пересчёт, победа, delta snapshot.

Боевой кулдаун измеряется в тиках, поэтому headless-ускорение не зависит от скорости выполнения цикла на CPU. Все вероятности используют `shared/rng.js`; UUID игроков и сетевые задержки не участвуют в RNG.

## 4. Атака и бой

Клиент передаёт:

```json
{
  "t": "CMD",
  "cmdId": "unique-command-id",
  "type": "ATTACK",
  "payload": { "fromRegions": [150], "toRegionId": 57, "percent": 50 }
}
```

Сервер проверяет фазу, мирный период, владельца, занятость источника, соседство/порт, числовой `percent` (включая `NaN`/`Infinity`), силу и cooldown.

- `force = floor(sum(sourceTroops) × percent / 100)`.
- Списание пропорционально начальным гарнизонам, остаток округления уходит из последнего источника.
- Для нейтрала: `defense = 1 + 0.5 × troops + 0.16 × sqrt(area)`.
- Для нации: `defense = troops × (1 + 0.10 × fortLevels)`.
- Fort уменьшает силу на 8%/уровень (ограничение 55%) и увеличивает длительность волны ×1.5.
- Морской десант получает `1 + 0.15 × portLevels` к силе.
- Захват происходит при `effectiveForce > defense`; остаток атакующих становится гарнизоном.
- При неудаче гарнизон защитника уменьшается на `effectiveForce / defenseMultiplier`.
- Если цель уже захвачена тем же игроком до прибытия волны, сила становится подкреплением.

Auto-expand после захвата выбирает самого слабого соседа и отправляет 65% оставшегося гарнизона. По умолчанию выключен.

## 5. Инфраструктура

На регионе может находиться до шести разных типов, каждый тип — один объект уровня 1–5. Повторная команда того же типа автоматически становится апгрейдом в UI; протокол также поддерживает явные `BUILD` и `UPGRADE`.

`maxHP = baseHP × level`. Пассивной регенерации нет. Апгрейд:

```text
newHP = min(newMaxHP, oldHP + 0.5 × newMaxHP)
```

Новые и улучшенные постройки учитываются сразу. Захваченные — только со следующего тика через `disabledUntilTick`.

### Захват построек

Для каждой постройки отдельно:

```text
hpRatio       = clamp(hp / maxHP, 0, 1)
forcePressure = clamp(effectiveAttack / maxHP, 0, 1)
pDestroy      = clamp(0.25 + 0.20 × (1 − hpRatio) + 0.15 × forcePressure, 0.05, 0.60)
```

Если постройка не разрушена, оставшиеся исходы делятся в исходной пропорции **40 intact : 35 damaged**. Это сохраняет базовые 40/35/25 при полном HP и отсутствии force pressure, а повреждение и чрезмерная сила повышают разрушение.

- `intact`: уровень и HP сохраняются.
- `damaged`: уровень −1 (не ниже 1), HP = 50% нового maxHP.
- `destroyed`: объект удаляется.

Все исходы пишут события `BUILDING_CAPTURE` / `BUILDING_LOST`.

### Автоматические системы

- Drone каждые 20 с ищет случайную вражескую постройку в радиусе 5. Полёт 1.2 с, урон 25×level.
- Missile каждые 60 с выбирает вражескую инфраструктуру в радиусе 12. Полёт 2.5 с, урон 120×level по цели и splash-геометрии 1.5.
- AA имеет одну попытку на батарею против снаряда. Дрон перехватывается гарантированно, если батарея готова; ракета — с шансом `min(90%, 25% × level)`.
- Если цели нет, drone повторяет поиск через 3 с, missile — через 5 с. Это предотвращает бесконечное ожидание полного cooldown при появлении цели.

## 6. ИИ

`server/ai/aiController.js` оценивает атаки и постройки на каждом decision tick.

Атака учитывает необходимую силу, берег, постройки, дистанцию, столицу и среднюю угрозу соседних гарнизонов. Процент рассчитывается от имеющихся войск и оценки защиты; бот не списывает ресурсы «из воздуха».

Строительные приоритеты:

- I: почти исключительно расширение, случайные паузы/ошибки.
- II: habitats.
- III: habitats + bastion столицы.
- IV: + ports и AA.
- V: + drones/missiles и более частые решения.

Mixed использует веса 15/20/30/20/15; выбранный уровень виден в лобби и лидерборде. Ошибки низких уровней реализованы вероятностью пропуска/неоптимального выбора, а не изменением формул.

## 7. Сеть и комнаты

- `GET /api/rooms` — открытые multiplayer lobby.
- `GET /api/health` — liveness.
- `GET /api/profile` — агрегированная JSON-статистика.
- `HELLO createSolo/createMultiplayer/join/resume` — вход.
- `WELCOME` — clientId, sessionToken и шестисимвольный код.
- `FULL` — полный authoritative state при старте/реконнекте.
- `SNAP` — dirty regions, все компактные player summaries, waves/projectiles и события.
- `ACK` / `ERR` — завершение pending command; client retry сохраняет `cmdId`.
- `RESULT`, `CHAT`, `SERVER_SHUTDOWN` — отдельные сообщения.

Каждый игрок имеет rate window 30 команд/с. Чат очищается от управляющих символов и ограничен 200 символами/700 мс. WebSocket payload ограничен 32 КБ.

При разрыве human-страна не участвует в AI-решениях 90 с. `resume` по room code + player id + token возвращает полный state. После timeout начинает действовать бот III; token всё ещё позволяет вернуть управление. `LEAVE` в активном матче сразу передаёт страну боту, в лобби — освобождает слот и при необходимости передаёт host.

## 8. Рендер и UX

- Базовый мир — `ImageData` 192×96; один drawImage с `imageSmoothingEnabled = false`.
- Цвета имеют 3 детерминированных оттенка, границы вычисляются по соседним клеткам.
- Паттерны владельцев дублируют цвет; selected/hover имеют отдельные контуры.
- Постройки, столицы, волны, снаряды и частицы — отдельный dynamic pass.
- `devicePixelRatio` ограничен 2. Камера ограничена 0.5×–8× от fit scale.
- При FPS <45 снижается число частиц. `visibilitychange` останавливает рендер и ставит соло на паузу.
- DOM HUD не создаёт Canvas-объекты под текст интерфейса.

Фактический Chromium profile: render pass около 1.0–1.8 мс на стартовой карте. FPS software headless не используется как показатель физического телефона.

## 9. Звук

Все сигналы создаются осцилляторами, noise buffer, biquad filter и envelopes. Микшер содержит master/SFX/music gain. Панорама и громкость зависят от координаты события относительно камеры. Одновременно разрешено шесть боевых сигналов; UI и победная последовательность имеют отдельные сценарии.

`localStorage` хранит `pf-audio`, `pf-session` и флаг завершённого туториала. AudioContext не создаётся до пользовательского действия.

## 10. Тестовые доказательства

- 27 `node:test` tests: формулы, бой, RNG, цены, HP, 0/100%, cap, max level, port/coast, busy region, drone, missile, AA, reconnect, связность/симметрия обеих карт, NaN/Infinity и protocol limits.
- Headless 8 mixed / seed 42: естественная Domination-победа на 271 игровой секунде, без NaN и нарушений owner↔region.
- Network smoke: два независимых клиента, одинаковый full snapshot, bot, start, chat, validation и reconnect.
- Chromium: чистая консоль, 0 внешних запросов, 360 px без horizontal overflow, реальные pointer actions для build/attack.
- Скриншоты: `docs/screenshots/`.

## 11. Сознательные отличия от расширенного технического плана

1. Нет viewport interest management; публичная информация передаётся dirty delta. Это безопасно только потому, что fog of war отсутствует.
2. Нет обещания zero-allocation loop. `ImageData` переиспользуется, частицы ограничены, но небольшие массивы snapshot/selection создаются.
3. JSON вместо бинарного протокола: 300 регионов и ограниченные dirty sets остаются компактными; бинарный codec имеет смысл после interest management.
4. Нет реального Redis/master процесса; транспортный контракт вынесен в `server/interfaces/gameServer.js`.
5. Порог 25% выбран для завершимой вертикальной кампании. Для классического total conquest установить `defaultWinPercent: 1`.

Эти пункты не скрыты за заглушками в UI и являются первыми кандидатами для V0.2.
